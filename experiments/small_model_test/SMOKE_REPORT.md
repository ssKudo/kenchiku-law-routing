# スモークテスト報告：小型モデルによる問題文の言い換え（検索語変換）

日時: 2026-11-12／本番（300問）は未実施。試し運転5問のみ。

## 結論（先に）

- **環境とモデルは問題なく動いた。** この VM で Qwen2.5-1.5B-Instruct（Q4_K_M）が llama.cpp で推論でき、日本語の応答も返る。
- **ただし、今回の素朴なプロンプトでは「条文用語への言い換え」はほぼ起きなかった。** モデルは用語を生み出す代わりに、問題文・選択肢の文や指示文そのものを写す、同じ語を繰り返す、といった挙動が大半だった。
- 数字の上でも改善は示せなかった：入口トップ3命中は変換前 1/5 → 変換後 0/5、正答条順位は5問中1問だけ改善（13位→7位）。
- **速度は実用圏。** 変換1問あたり約30秒（モデル読み込み込み）。300問なら約2.5〜3時間（後述の常駐化で約2時間弱まで短縮見込み）。
- 仮説が否定されたわけではなく、「1.5B にゼロショットで言い換えさせる」方法が弱い、という結果。本番前にプロンプト（少数例の提示）と出力の後処理を決める必要がある。

## 条件

- モデル: Qwen/Qwen2.5-1.5B-Instruct-GGUF Q4_K_M（約1.12GB）、llama.cpp b12314 `llama-completion`、スレッド4、temperature 0.2、seed 42、最大160トークン
- プロンプト: 「問題の根拠条文を探すための検索語（条文で使われる専門用語）を最大8個、『、』区切りリストのみで出力。説明文・条文番号は書くな」という趣旨（全文は smoke_results.json の meta に記録）
- 検索: (c) 本格版ステージ3と同一の TF-IDF エンジン（engine.py）を再利用。ベースライン = 問題文＋選択肢、変換後 = ベースライン＋変換語（各1回、空白区切り連結）
- 設計判断: モデルが出力した「第○条」だけの語は、条番号の当て推量を混ぜないため検索語から除外し、別途記録した（今回の5問では該当なし。ただし事前の動作確認プロンプトでは第106条〜第112条のような根拠のない条番号列挙が実際に出た）

### モデル出力の実態（正直な内訳）

- **写しが大半**: 「開発許可を受けた開発区域内の土地においては」「収容人員が10人の飲食店と」など、選択肢の文の切り取りが検索語として返った。言い換え（日常語→条文用語）はほぼ起きていない。
- **指示文のエコー**: 「条文で使われる専門用語」という指示文自体が語として混入（2022-24、2024-28）。
- **繰り返し崩壊**: 2024-28 では「建築物の耐火性、耐火構造」が8回繰り返され、しかも話題が正答（法12条＝定期報告）から逸れた。
- **完全な失敗**: 2022-28（省エネ）は出力が「イ、ロ、ハ」だけ（選択肢の小項目記号の鸚鵡返し）。
- **唯一の改善例**: 2020-25（消防法）は、写した文の中に条文用語「防火管理者」が含まれており順位が 13→7 に上がった。「条文用語がクエリに足されると TF-IDF が応える」という仮説の mechanism 自体は垣間見えた。ただしこの改善は「言い換え」ではなく「写しによる重み付け」の効果と区別がつかない。

## 速度

- 変換1問あたり: 平均28.4秒、典型値 約29〜34秒（プロセス起動＋モデル読み込み 約7秒を含む）
- 内訳の目安: プロンプト処理 41〜47 トークン/秒（1問 412〜597トークン）、生成 約11 トークン/秒
- **300問換算: 約2.5〜3時間**（今回の起動方式のまま）。llama-server 常駐でモデル読み込みを省けば約21〜24秒/問 → **約1.8〜2時間**の見込み

## 本番（300問）前に決めるべき点

1. **プロンプトに少数例（few-shot）を入れるか** — 良い変換例を2〜3件示すのが 1.5B には一番効きそう。今回の失敗の大半は形式の崩れであり、例示でかなり直る可能性がある。
2. **後処理の方針** — 指示文エコーや見出し行の除去、長すぎる語（文の切り取り）の棄却、重複語の圧縮をどこまでやるか。
3. **付け足し方針** — 問題文に既にある語の写しを足すと「重み付け」として効いたりノイズになったりした（対照問は 2位→4位に悪化）。「問題文に無い語だけを足す」に限定するかは設計判断として要決定。
4. **モデルの格上げを試すか** — Qwen2.5-3B（Q4で約2GB、メモリには収まる）や Qwen3-1.7B との比較を、本番前に同じ5問で先にやる価値がある。
5. **実行方式** — 本番は llama-server 常駐＋バッチ投入が無難（起動コスト削減と失敗時の再開が容易）。
