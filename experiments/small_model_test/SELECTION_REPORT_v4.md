# 選択実験 v4 報告（few-shot：実例2件を見せてから言葉を選ばせる）

日時: 2026-11-12
対象: v1〜v3 と同じ5問（2017年 学科III No.21, 22, 24, 4 と対照 No.1）
モデル: Qwen2.5-1.5B-Instruct GGUF Q4_K_M（llama.cpp、temp 0.2、seed 42）
実例: 2018年 No.2 / No.1（fewshot_examples.json、候補リストと選択はファイルのまま）
検索: (c) 本格版ステージ3と同一の TF-IDF エンジン
生データ: selection_results_v4.json（サンプルプロンプト全文・生出力・パース結果・秒数を含む）
実行スクリプト: selection_test_v4.py

## 結論（先行）

**few-shot でも「内容で選べた」とは言えない。** 出力の「形」は v3 より整ったが、
順位と命中では v3 からも baseline からも一歩も前進しなかった。

整った点: v3 で3問に出た「リストを先頭からほぼ全語写す」挙動は後退し、
完全な先頭8語コピーは対照問（No.1）だけになった。末尾寄りの語まで届く選択や、
v3 で選択ゼロだった No.24 の選択成立など、実例が「飛ばして8語選ぶ」型を
部分的に伝えた形跡はある。

しかし選ばれた語の並びは依然としてリストの昇順走査が支配的で、
「どれを優先するか」の判断には実例の効果が届かなかった。その結果、
正答条の順位は baseline 比で改善した問がゼロ、トップ3命中も 1/5 のまま。
壁は「形式の崩れ」から「優先度付けの判断」へ移った、というのが正確な読み。

## v3 からの変更点（本番の問題・リスト・モデル・温度・seed は同一）

1. プロンプト冒頭に実例2件を入れた。構成: 指示 → 【実例1】 → 【実例2】 → 【本番の問題】。
   実例の選択は、先頭8語と意図的にずらしてある「内容で選ぶ」見本（ファイルのまま使用）。
2. 指示文に数字の例示は入れていない（v1 の轍を回避）。
3. llama-completion のコンテキスト長だけ -c 8192 を明示（プロンプト長の都合。
   サンプリング条件への影響なし）。
4. 候補リストは作り直していない。baseline / oracle は v1、v3 比較値は v3 の実測を再掲。

## 生出力の実態（診断）

- No.21: リスト内8語ちょうどの出力で上限を遵守（この問は v3 では17語出力）。
  選ばれた語はリストの 2, 4, 5, 6, 7, 17, 18, 20 番目で、末尾の「集会場」
  「延べ面積」「登録」まで届いた。ただし並びはリストの昇順のまま。
  リスト外は「建築士」（リスト語の切り取り）1語のみ。順位は 5 位で不変。
- No.22: リスト内15語をリスト順に出力し上限超過（v3 の19語よりは減ったが質は同じ）。
  採用8語は先頭寄りに偏り、順位は baseline 7 位 → 8 位と v3 同様に悪化。
- No.24: v3 の「リスト外の1語のみ・選択ゼロ」からは前進し、リスト内11語の選択が成立。
  ただし前置きの文（「都市計画法上、誤っているものは以下の通りです。選んだ言葉:」）
  を出力し、「説明は書くな」に違反。並びはほぼ昇順で、oracle 命中を担う語群
  （地区整備計画・仮設の建築物・着手する日の30日前）は出力の9〜11番目に現れたため
  8語枠の切り捨てで落ち、順位は 5 位（oracle の 3 位に届かず）。
  「良い語を選べても、優先順位を付けて前に並べられない」ことが損失に直結した例。
- No.4: v3 で唯一「写しでない選択」をした問。v4 では採用5語（上限内）と数は適正だが、
  リスト外の改変語（「高さが60mを超える建築物」＝リスト語への付加、
  「確認があった旨」＝選択肢由来）が混じり、順位は v3 の 9 位 → 10 位に後退。
  few-shot が v3 の良い挙動を安定させる効果は確認できなかった。
- No.1（対照）: リスト内12語を完全にリスト順に出力し、採用8語は先頭8語と完全一致
  （common_prefix 8/8）。v3 と同じ先頭コピーで、実例の効果はこの問には出ていない。
  順位は1位を維持。

### 形式面の遵守
- 「最大8個まで」: リスト内出力数で見ると No.22（15語）、No.24（11語）、No.1（12語）の
  3問で超過。超過した問の数は v3 と同じ3問だが、顔ぶれは入れ替わった
  （No.21 が遵守側に回り、No.24 が「選択ゼロ」から「超過」に変わった）。
- 「リストに無い言葉は書くな」: 完全な無関係語の混入はなし。ただし No.24 の前置き文、
  No.4 の改変語2語、No.21 の切り取り語1語がリスト外として記録された。
- 実例の丸写し: 検出フラグは No.24 / No.4 の「建築物」のみ。だがいずれも本番リストの語
  （既存の建築物、高さが60mを超える建築物）の一部として文字列が現れたもので、
  実例2の選択語「建築物」が独立した語として混入した例はない。実質的な丸写しはゼロと判断する。

## 失敗の切り分け

- リストの質（oracle 上限 2/5）は不変で、No.21, 22, 4 は全語を足してもトップ3未満。
  この天井自体は今回も変わっていない。
- v4 で新たに分かったこと: 実例は「出力の形」（8語前後で止める、飛ばして選ぶ、
  末尾まで目を通す）には効いたが、「どの語が正答条への橋になるか」の優先度付けには
  効かなかった。選択は全問でリストの昇順に強く引きずられており、良い語が
  後ろに並ぶと8語枠で落ちる（No.24 が典型）。
- つまり残る壁は2層: (1) リスト自体の判別力（oracle 2/5）、
  (2) 1.5B の優先度付けの判断力。few-shot は (2) のうち「形式」の部分だけを直した。

## 速度

モデル呼び出しは1問あたり 38.8〜44.0 秒（平均 約40.8 秒、5問合計 約204 秒）。
v3（平均 約26.5 秒）の約1.5倍。実例2件ぶんプロンプトが長くなった影響。

## この結果の意味と、次にやるなら

- 「例を見せれば選べるようになる」という仮説は、少なくとも実例2件・この形式では
  支持されなかった。形は整うが中身（優先度付け）が伴わない。
- v3 報告で挙げた残りの候補:
  1. **3Bモデルとの比較** — 同じ5問・同じ v4 プロンプトで Qwen2.5-3B にやらせ、
     壁がモデルの大きさの問題か形式・タスクの問題かを分ける。優先度付けの判断が
     サイズでどう変わるかを見るには、v4 の物差しがそのまま使える。
  2. **リストの作り直し（盲検のまま）** — oracle 2/5 の天井問題は依然として残る。
  3. 実例の増量や実例への「なぜ選んだか」の付記は、(2) の判断力を直接教える方向だが、
     実例づくりのコストと見合うかは 3B 比較の結果を見てからでも遅くない。
- なお対照問（No.1）は全条件で1位を維持。語を足すこと自体の破壊力は引き続き小さい。
