# 選択実験 v5 報告書 — 1語ずつの○×判定なら務まるか

## 結論

**務まらなかった。ただし失敗の形はこれまでと正反対で、全97判定が「×」だった。**

- 候補リストの全語（5問・計97語）を1語ずつ独立に判定させたところ、○は **0個**。正答条の橋語19語も全て×だった。
- ○が0語のため、binary-words 条件のクエリは問題文のみ（＝baseline と同一）になり、順位は全問 baseline と同値。新しい命中はゼロ。
- 一方で**形式は全バージョン中で最も完璧**だった：97件全てが「×」1記号だけのクリーンな出力で、形式崩れ・判定不能は0件。再試行なし。
- つまり「○か×だけで答える」という**出力形式は 1.5B の能力内**だが、「役立つかどうか」の**判定内容が全て否定に倒れ、語による弁別が一切働かなかった**。「全部○（v3 の写し・過剰出力）」の鏡像として「全部×」になった。

なお測定後、同じプロンプト・同じ条件で llama-completion（v1〜v4 と同じ経路）により4語（正答条の橋語を含む）を再判定し、4件とも×を再現した。全×はサーバ／キャッシュ経路の異常ではない。

## 方法

- モデル: Qwen2.5-1.5B-Instruct GGUF Q4_K_M、llama-server 常駐＋プロンプトキャッシュ、temperature 0.2、seed 42、生成上限16トークン。対象・候補リストは v1〜v4 と同一（作り直しなし）。
- 判定は1語ごとに独立したプロンプトで行った（実例なし＝ゼロショット、数字の例示なし）。プロンプト文面は selection_results_v5.json の meta（user_template）に全文記録。
- ○の語は上限を設けず全て採用（8個枠なし）。パースは「最初に現れる○または×類を判定」とし、余分な文がある場合は format_dirty として数える。再試行・補正はしていない。

## なぜ全×になったか（観察と解釈）

事実として言えるのは「このプロンプトでは、役立つ語にも一律に×が返る」ことまで。機構の解釈としては次の可能性が考えられるが、本実験だけでは切り分けられない。

- 問い方「この言葉は根拠条文を探すのに役立ちますか」が厳密に読まれ、「その語だけでは条文は特定できない」→×、と全語に適用された可能性。
- 小型 instruct モデルの否定側への偏り（安全側の答えとして×を選ぶ）。

いずれにせよ、v3/v4 の「選べと言われると過剰に出す」に対して、v5 は「1語ずつ聞かれると全部落とす」。**タスク分解を変えても、1.5B の判断が語の内容に追随しない**という点では一貫している。

## 速度

- 判定97件で計207.0秒、**1判定あたり平均2.13秒**。内訳は各問の初回が約7〜10秒（問題文の全処理）、2件目以降はプロンプトキャッシュ（337〜448トークンを再利用）で約1.7〜1.8秒。
- **1問あたりの総時間は約36〜44秒**（判定約20件＋採点）。判定件数が多いため、v4（約41秒/問）と同水準にとどまった。なお llama-completion を判定ごとに起動する方式では1件約13秒かかることを事後確認で観測しており、常駐化の効果自体は大きい（約1/6）。
