# 選択実験 v2 報告（番号例の除去＋リスト順シャッフル）

日時: 2026-11-12
対象: v1 と同じ5問（2017年 学科III No.21, 22, 24, 4 と対照 No.1）
モデル: Qwen2.5-1.5B-Instruct GGUF Q4_K_M（llama.cpp、temp 0.2、seed 42）
検索: (c) 本格版ステージ3と同一の TF-IDF エンジン
生データ: selection_results_v2.json（プロンプト文面・生出力・パース結果・秒数を含む）
実行スクリプト: selection_test_v2.py

## 結論（先行）

**番号例を消しても、モデルは「読んで選ぶ」をしなかった。** 10回すべて、出力は
連番の羅列（例: `1, 2, 3, 4, 5, 6, 7, 8` / `3, 4, 5, 6, 7, 8, 9, 10`）で、
v1 の「例示のなぞり」ではなかった。**例が無くても連番を並べる**のがこのモデルの
素の挙動で、「番号で選ばせる」という出題形式そのものが 1.5B には向いていない、
という一段強い否定的な結果になった。

順位の上では A（元の順序）トップ3命中 1/5、B（シャッフル）2/5 だが、
これは baseline 1/5・oracle 2/5 と同じ水準のノイズで、「選んだ」証拠ではない。
No.24 の B で2位になったのも、シャッフル後の先頭8個にたまたま橋語が
固まっていたためで、内容による選択ではない。

## v1 からの変更点（リスト・問題・モデル設定は同一）

1. 指示文から番号の具体例「（例: 3, 7, 12）」を除去。
   「出力は番号だけをカンマ区切りで書いてください。説明や文章は書かないでください。」のみ。
2. 同じリストを2つの順序で出した。A=元の順序、B=シャッフル（random seed 7）。
   語で追うことで、番号追随か内容追随かを判定できるようにした。
3. リスト自体は作り直していない。正答条を見て直すと oracle が汚染されるため。
   oracle は v1 と同じ値になるはずで、ここでは再掲のみ。

## 生出力（全10回、整形なし）

- No.21 A: `3, 4, 5, 6, 7, 8, 9, 10` / B: `5, 6, 7, 8, 9, 10, 11, 12`
- No.22 A: `2, 3, 4, 5, 6, 7, 8, 11` / B: `1, 2, 3, 4, 5, 6, 7, 8`
- No.24 A: `2, 3, 4, 5, 6, 7, 8, 9` / B: `1, 2, 3, 4, 5, 6, 7, 8`
- No.4 A: `2, 3, 4, 5, 6, 7, 8, 9` / B: `5, 2, 3, 4, 16, 17, 18, 19`
- No.1 A: `1, 2, 3, 4, 5, 6, 7, 8` / B: `1, 2, 3, 4, 5, 6, 7, 8`

10回中9回がほぼ完全な連番。No.4 の B だけ後半が `16, 17, 18, 19` と
飛んでいるが、これも連番の塊が2つ並んだだけで、内容による選択ではない。
形式面（番号のみ・8個以内・範囲内）は v1 同様に全問合格。

## シャッフル判定（語で追った結果）

A/B で選ばれた語の重なりは 3〜5語/8語（No.21: 5、No.22: 3、No.24: 3、No.4: 4、No.1: 3）。
両方とも「先頭8個の連番」を選ぶ挙動だと、20語中8語ずつの重なりは
偶然でも平均 3.2語になるため、この重なりは偶然の水準でしかない。
**語が順序を超えて安定して選ばれた証拠はない。**

## 速度

モデル呼び出しは1問あたり 17.3〜35.0 秒（平均 約21.0 秒、10回合計 約210 秒）。
v1（約23.6 秒）と同水準。

## この結果の意味と、次にやるなら

- 「番号で選ばせる」は、例示の有無にかかわらず 1.5B の素の挙動（連番の列挙）と
  相性が悪い。**選択形式そのものを変えない限り、同じ壁に当たる**と見るのが正直。
- 形式を変える候補（いずれも未実施）:
  1. **例を見せてから頼む（few-shot）** — 「こういう問題文 → こういう検索語」という
     実例を2〜3個先に渡す。生成実験（スモークテスト）の次手としても挙がっていたもの。
     ただし選択形式のまま例を入れると v1 の「例のなぞり」が戻るおそれがあり、
     例は「語の出し方」の例にする設計が要る。
  2. **語そのものを書かせる（生成に戻る）** — 番号ではなく検索語を直接書かせる。
     スモークテストでは写し・繰り返しが多かったが、few-shot と組み合わせるのが筋。
  3. **3Bモデルとの比較** — 同じ5問・同じプロンプトで Qwen2.5-3B に選ばせ、
     壁がモデルの大きさの問題か、形式の問題かを分ける。
  4. **リストの作り直し（盲検のまま）** — oracle が 2/5 のままでは、仮にモデルが
     正しく選べても届かない問が残る。ただし正答条を見て直すのは汚染になるため、
     直すなら「問題文＋種条文の周辺から機械的に拾う」など盲検の方法で、が条件。
- なお、対照問（No.1）は A/B とも1位を維持し、悪化はなかった。
  語を足すこと自体の破壊力は小さい。

## 診断メモ（リストの質について、v2 実行前の分析）

候補語の文書頻度（全1,811条中、その語を含む条数）を調べた結果、リストの語の
大半は問題文・選択肢の中に既にある語で、足す効果は「重み付けの上乗せ」
（エンジンはクエリのグラム数を3で頭打ちする）に留まる。問題文に無い新しい語は
各問2〜3語しかない。また正答条の条文テキストに実際に含まれる語（橋）は
No.21 で4語、No.22 で2語、No.4 で3語と薄い。これが oracle 2/5 の背景。
この分析はリスト設計の参考用で、v2 のリスト自体には反映していない。
